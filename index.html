UI Harness — a gated agent pipeline that turns a written brief into a built, validated screen

Scope. A single-operator tool with one user: me. Every number below is engineering measurement rather than traffic.

Summary

I build a mobile game solo. Authoring a UI screen was the slowest part of that: a screen is a layout decision, an art decision, a set of named bindings, a Unity hierarchy and a C# script, and every one of those steps drifts from the one before it.

So I built the pipeline that does it. A 19-node LangGraph graph runs 10 role-specialised agents behind 5 human approval gates. Typed Pydantic contracts are the canonical artifact — Markdown, HTML mockups and rendered PNGs are generated views of the contract, never the source of truth. Nine deterministic validators plus a scored screenshot-vs-mockup comparison act as an evaluation harness with enforced thresholds (0.85 overall, 0.70 per dimension); a failure does not just stop the run, it routes back by conditional edge to the stage that caused it. Every stage is routed to a model and reasoning effort, carries token/turn/tool budgets tuned from measured runs, and reports reported_cost_usd into an append-only event ledger. State is checkpointed in SQLite, so a killed run resumes. The pipeline also exposes itself as an MCP server, so an external agent front-end can drive it.

~15,300 lines of Python 3.12 with 259 tests. Across the run ledgers on disk: 18 worker executions carrying $17.03 of reported spend, 287,290 output tokens, and a 74% context-cache read ratio — 3.41M cached-read tokens against 458 fresh input tokens.

It is entirely my own work.

(Both images are artifacts of one recorded run, combat-screen-6643dafd0c.)

The problem

Not "I wanted to try agents". The bottleneck was specific and it was mine.

A screen in this project costs a day or more of hand-wiring, and the expensive part is not typing — it is that four separate decisions get made in four separate places and silently disagree: what goes where, what it looks like, what the elements are called, and what the code binds to. Rename an element in the layout and the script's serialized field stops resolving. Let the art step reposition something and the built screen no longer matches the thing that was approved.

I had already solved the human version of this problem on a previous team, by hand: product intent was reaching the concept artist before requirements existed, so full-fidelity art was being produced and then reworked. I inserted a structural mockup step in between — plain blockouts, no final art — so layout and affordances got settled while they were still cheap to change, and the artist received something executable.

The harness is that same workflow expressed as software: structure first, aesthetics second, each behind a gate, with a typed contract carrying the agreement forward instead of a human remembering it.

Constraints

These are what made the design non-obvious, and they are why several of the decisions below go against the grain of the usual agent-framework demo.

  1. The output is not text — it is a mutation of a Unity project. A wrong answer is not a bad paragraph, it is a broken scene in the repository I ship from. Read-only stages must be provably read-only; exactly one stage may write to Unity.
  2. Model spend is my own money. A run that burns $5 and produces something I reject is a real cost. Every design choice had to answer "what does this cost per run, and what did the money buy".
  3. A model is not deterministic and I refuse to pretend otherwise. The pipeline has to assume any stage can return something structurally wrong, and still not lose the paid work that came before it.
  4. I am the only reviewer. No team to catch drift. Whatever the machine cannot check, nobody checks — which is why validation had to exist before features.
  5. Two providers, two CLIs, one workstation. Claude Code and OpenAI Codex CLI, driven as subprocesses, with all the operating-system reality that implies (see the failure section — one of them was silently unavailable for weeks).

What I built, and what I rejected

Typed contracts as the canonical artifact

Every stage's output is a Pydantic model. The layout contract for one screen is ~2,000 lines of JSON with absolute geometry; the human-readable spec and the HTML/PNG mockups are rendered from it.

The alternative I rejected: passing Markdown between agents, which is what most agent pipelines do. It fails at exactly the point this pipeline exists to fix — there is no mechanical way to check that the built screen matches an approved prose description, and prose invites each stage to re-interpret the last one. A contract can be validated, diffed, and compared against a screenshot. It also means the schema is the interface: when a worker returns something invalid, that is a caught error rather than a plausible paragraph that fails three stages later.

Human gates, with rejection routed to the causal stage

Five gates: readiness, sketch, layout, art, final. Approval advances; rejection is a conditional edge back to the stage that produced the problem, carrying my rejection text as that stage's feedback input.

The alternative I rejected: re-running the pipeline from the top, or letting the model decide when it is done. Restarting throws away paid work that was fine. Fire-and-forget autonomy is cheap to build and, for an output that mutates a shipping repository, is the wrong trade: at those five points a human decision costs less than a bad write into the repository.

An evaluation harness, built before the features

Nine deterministic validator modules (geometry, naming, compilation, assets, code rules, rect comparison, Unity live/state, mockup measurement) plus a scored comparison of the final screenshot against the approved mockup, with enforced thresholds: 0.85 total and 0.70 on every individual dimension. A run does not advance on a failing score.

The validators are the reason the rest of the system can be trusted, and they are also where the honest engineering is: rect_compare exists because Unity reports sizeDelta where the naive check reads size, and the two disagree in the exact cases that matter.

Deterministic repair before failure

When a worker returns schema-invalid output, the harness first tries to repair it mechanically and records a deterministic_repair_applied event; only then does it fail. Example: duplicate element names used to kill a run — a whole run, including the most expensive stage in the system — over a name collision that code can resolve by the same numeric-suffix convention a human would use.

Repairing mechanically before failing is a cost decision: a model call spent on a problem a string function solves is wasted money and added latency.

Advisory budgets that never discard paid work

Per-stage output, turn, tool-call and wall-time budgets, tuned from measured runs. A breach emits a warning; it does not kill a worker that has already produced a valid paid result. Input estimates are still checked before launch, where the money has not been spent yet, and there is a separate optional hard kill switch, unset by default.

The alternative I rejected: hard caps, which I ran first. They abort a stage at 95% completion and bill you for all of it.

Per-stage model and reasoning-effort routing, with provider fallback

config/models.yaml routes each stage to a provider, model and effort tier, with fallback chains and executable discovery. Cheap deterministic stages use no model at all.

Context assembly: caching, then retrieval

Workers receive a stage-specific context packet — the contract artifacts they need, the selected rule sections, their prompt, the current causal feedback, their allowed tools and their output schema. They never receive previous stages' reasoning transcripts. Packets are cached by content hash, which is where the 74% cache-read ratio comes from: 3.41M cached-read tokens against 458 fresh input tokens across the instrumented runs.

That is caching, and for a long time I was careful to call it caching, because it is not retrieval.

Retrieval came later, and for a concrete reason. The pipeline keeps an append-only, never-deleted log of everything it has got wrong — a 216-line live log and an 848-line archive. The readiness stage was being handed the live half of that log in full on every run, while the archive — the larger half, and the half holding the resolved cases with verified fix recipes — was visible to no stage at all. Archiving an entry was hiding it.

So the log is now retrieved rather than pasted: heading-boundary chunking over the advisory corpus, a hybrid index — bge-small-en-v1.5 locally through ONNX, fused by reciprocal rank with a dependency-free lexical channel, over sqlite-vec — with an incremental build that never re-embeds unchanged text.

Three boundaries I set deliberately:

  • Only advisory corpora are retrieved. Typed contracts and generated code are passed whole. They must reach a stage complete and exact; a partially-retrieved contract is a corrupt contract.
  • A stage never retrieves a corpus it already receives whole. Readiness gets both style bibles in full, because its job is to report what the bibles lack — and absence is only evidence when the reader saw everything.
  • Retrieval never fails a run. Any error falls back to the previous whole-file sourcing and records the reason in the run's context_compiled event.

Measuring the retrieval instead of asserting it

A 32-pair gold set built from real history: for each past failure, which archived entry or bible section should have come back. The queries are phrased the way a rejection is actually phrased, not in the wording of the entry they target, so the score measures retrieval rather than string matching.

And the honest reading, which is the part I care about more than the numbers: at 32 pairs, one pair is worth 0.031 of recall, so fusion's wins at k=3 and k=10 and its loss at k=5 are all inside the resolution of the set. They are not results. Fusion ships for two reasons the data does support — the best recall@10, and a single code path whether or not the optional dense dependency is installed, which keeps the fallback exercised rather than dead.

The one tuning decision the set was large enough to settle: weighting the rejection feedback 8× the stage objective moved fused recall@5 from 0.625 to 0.812 and MRR from 0.409 to 0.663. The reasoning came before the measurement — a stage's objective barely changes between two attempts at the same screen, so it cannot discriminate between two failures, while why the last attempt was rejected is exactly what is being looked up. I chose 8 rather than 16 because 28 of the 32 pairs share one objective, which flatters any weight that discards the objective entirely.

Durable execution and recovery

SQLite checkpointing with resume, an append-only event ledger per run, and failure→stage recovery routing by owner. Read-only stages are mutation-checked at runtime.

An MCP server

The pipeline exposes itself over MCP, so an external agent front-end drives it rather than everything living behind a CLI I wrote. A desktop operator app (Rust/Tauri + React over a Python core) talks to it that way.

What went wrong

Three things worth telling, because they are the ones that changed how I build these systems.

1. Every stage breached its budget, so the budget signal was dead

Measured from the ledgers: readiness had an output budget of 4,000 against observed values of 4,115 / 4,767 / 5,037 / 5,480 / 5,998 / 8,344 and one 17,284 outlier; technical_design 40,000 against 40,441 and 47,043; art_direction 10,000 against 20,593. Every one of the 15 executions on the ledger at the time breached its budget.

A limit that everything always breaks is not a safety mechanism — it is noise that hides the one genuine blow-up you needed to see, and it trains the operator to ignore the only channel that would report it. I had set those numbers from intent. I re-tuned them from the ledger at roughly p100 × 1.2, and every breach since is a real signal.

What it taught me: budgets set from what you think a stage should cost are a guess wearing the costume of a control. They are only a control once measurement exists.

2. The provider fallback chain did not exist

The config advertised a three-provider chain. When Claude failed on one run, the recorded fallthrough read codex: Executable probe failed with exit code 1; openhands: … — so a single provider failure was terminal while the message implied three workers had been tried.

Root cause: the probed executable was the npm .cmd shim, which resolves node from PATH. The operator service's environment has no node, so cmd.exe exits 1 — and the identical command succeeds in an interactive shell, which is exactly why the probe "worked when I tested it". Fixed in three parts: discovery now prefers the vendored native binary that needs neither node nor cmd.exe; probe failures carry the process's stderr tail instead of a bare exit code; and the intake stage now writes a provider_availability event so every run states up front which fallbacks it actually has.

What it taught me: a redundancy you have never observed failing over is a claim, not a feature. The fix that mattered was not the discovery glob — it was making availability an event on the ledger.

3. The system's own memory was working against it

Covered above: archiving a resolved entry removed it from the pipeline's context entirely, so the record of a solved problem stopped being available as precedent at the moment it became most useful. It is the reason retrieval exists here at all, and it is why I keep a triaged, never-deleted defect log rather than a tidy one.

Scope

  • One operator. The harness serves my own pipeline, on my own workstation. The figures are engineering measurement.
  • Local by design. Local CLIs, SQLite and a desktop installer, chosen because the output is a mutation of a repository on the same machine.
  • The gold set is 32 pairs. Enough to settle a large effect, not a small one.
  • The corpus is live. Two new feedback entries move every retrieval number, so the figures carry the date they were taken.

Stepland — eight months on a live commercial mobile game, on two stores

Attribution. One of three core programmers inside a larger team. Systems that are mine are named with their line counts.

Summary

Stepland is a habit-tracking lifestyle game: real-world walking, hydration, meditation and exercise feed a Tamagotchi-like virtual pet. It is live on Google Play and the Apple App Store, free-to-play with ads and a subscription, localised in English, Catalan and Spanish. Anyone can install it and check every screen described here.

I worked on it from July 2025 to March 2026 as a technical designer and gameplay programmer, in Godot 4.6, in a core programming trio inside a larger team. 128 files in the shipped game were created by me, and 7 of its 16 services are mine. I also represented the studio on-stand at four industry events: Gamescom 2025, Godot Fest, BCN Game Fest and 4YFN 2026.

Three parts of this are worth reading first:

  1. I replaced a third-party dependency that was costing us players during onboarding with an in-house Android plugin, written in Kotlin — a language I had not used — in a week. StepSensorManager.kt is 211 of its 212 lines mine. It has been stable since.
  2. I rebuilt the game's tutorial as 82 declarative steps behind a sequence runner, by driving coding-agent sessions in a production repository, and it landed on the opening day of a trade-show showcase.
  3. I inserted a structural-mockup stage between product intent and final art, because art was being produced before requirements existed. The screens below show my blockout next to the shipped result.

Replacing the step-counting dependency

Stepland's core mechanic is counting the player's real steps. Everything else in the game — the pet, the currency, the streaks — is downstream of that number being correct.

Our implementation read steps through Google Health Connect, a third-party hub. That had three consequences at the point where they are most expensive, first launch:

  • A large share of players did not have Health Connect installed at all.
  • Health Connect is only a hub; it needs its own separate step-recording connector, so onboarding became a two-app setup unrelated to Stepland.
  • Misconfiguration failed silently — Stepland displayed "connected" while receiving zero steps. To the player, that is not a misconfigured hub. That is Stepland being broken.

The cost was retention, before players ever reached the game.

I proposed replacing it with an in-house plugin reading the Android pedometer directly. It was a significant architectural change and the team wanted to exhaust the existing approach first, which took about four months. When it was agreed, I built the replacement in a week, in Kotlin, which I had never written — working from references and pattern recognition.

What shipped: no third-party dependency, no second app, no silent zero-step state. One "allow pedometer access" prompt at first launch. Steps continue to accrue with the app closed, via a WorkManager snapshot scheduler and worker. It has been stable since.

Rebuilding the tutorial, against a showcase date

The original tutorial was built by a colleague earlier in the project and had been outgrown. I built its replacement: 82 declarative steps across 32 polymorphic step classes, behind a sequence runner with resume-from-index and per-step telemetry. It accounts for about 76% of the tutorial code surviving in the shipped game.

Two things make this more than a rewrite.

It was declarative on purpose. A tutorial that is a hard-coded sequence of special cases cannot be reordered, A/B-ed or resumed. Making each step a class behind a runner means the tutorial becomes data — and resume-from-index means a player who drops out of onboarding does not restart it, which is the point at which tutorials usually lose people.

I delivered it by driving coding-agent sessions, in a production repository, under a fixed date. The push ran 2026-02-17 → 2026-03-02 and landed on 2 March 2026 — the opening day of the 4YFN showcase (2–5 March 2026), immediately before the release candidate was cut.

I drove agent-assisted implementation and owned the result, in a shipping commercial codebase, against a deadline that did not move. It is the one piece of agentic engineering I have done where the product was someone else's.

The tradeoff: the tutorial ships without a service boundary of its own. Every other system I built here has one. This one was scoped against the showcase date, and I chose the deadline. I know what the debt is and where it is.

I made myself the stage in between. Requirements got argued while they were still cheap to change.

The one that is not a comparison

The streak screen is not a mockup that was replaced. I blocked it out directly in Godot, and it is still live, essentially unchanged, in a commercial product. The design half of the job

I was not only implementing features handed to me. The design work is documented, and it reasons about retention rather than describing screens:

  • A diagnosed onboarding problem, not a complaint about it: the first-time experience "feels like following a check-list" and runs out in 5–10 minutes, before the player is hooked — with a stated target of holding a player for at least 30 minutes.
  • Return timing treated as a design problem: the player has no way of knowing when to come back, so the design prescribes an explicit time horizon, in-app step feedback as a proxy for idle progress, and a notification at the point the resource fills.
  • A two-tier task system with a stated purpose per tier — progress tasks give direction, daily tasks give a reason to return — staged with escalating rewards, tied to both real-world actions and in-game ones, with premium currency deliberately placed on the behaviours the game wants to reinforce.
  • Economy analysis in the working vocabulary: revising sources and sinks, and the specific diagnosis that the game had many one-time sources, many recurring sources and many one-time sinks — but lacked recurring sinks.
  • A design principle I hold and can defend: never pure RNG. Give NPCs recurrent, discoverable patterns — players who detect randomness disengage; players who detect a pattern keep playing.

The design→build loop closes on the task system: I specified the two-tier design, argued for it, and then created tasks_service.gd and all 25 task definitions from nothing.

Dungeon Heroes — a real-time action roguelike, designed, built and shipped alone

Release status. As of August 2026 it is in closed testing on Google Play with the required 12 testers and the 14-day clock running. It is not publicly listed yet.

Summary

Dungeon Heroes is a real-time action roguelike whose abilities are delivered as cycling cards. It is not a turn-based card game — the cards sit inside a live fight with attack tells, interrupts and a parry window, so most card-game intuitions do not transfer.

I built it alone: design, programming, art, UI, release engineering and store compliance. 319 commits over ~12.5 months, 119 C# scripts, ~20,100 lines, Unity 6000.3.19f1, Android arm64 and armv7. Signed release AABs through v0.5.1.

The prototype came first and came fast — about a week, in June 2025, before the repository existed. That prototype is also why a studio contacted me a month later. When citing 319 commits, that first week is not in them.

The design problem

A card game gives you time. You read the board, you count mana, you commit. Every intuition that comes with the genre — from Slay the Spire, Magic, Hearthstone — is built on that pause, and none of it survives contact with a real-time fight.

Dungeon Heroes has no pause. The rules that create the experience:

FactValue
Hand4 slots, auto-refilling ~0.5s after a card leaves
Energymax 4, +0.5/s passive, starts at 0, +1 per successful parry
Castinglocks the hero for 0.42–1.5s — no block, no parry — and the effect lands at cast end
Enemiesone acts at a time, FIFO by readiness, 1.5s global gap (0.5s after an interrupt)
Attack tell0.8–1.2s wind-up with a white flash 0.5–0.7s before impact
Per-enemy cooldown5–9s between that enemy's own actions
Blockhalves damage while held; armor shatters on any hit unless the run has Bastion

The consequence those numbers create is the actual game. With two or three enemies alive, a tell arrives every 2.5–4 seconds, and that gap is the only place card play can happen. Casting inside it is a bet: the cast lock removes your defence for up to a second and a half, and the payoff lands at the end of the animation rather than the start. Against a lone enemy — most tier-1 fights, and every elite and boss — the window stretches to that enemy's 5–9 second cooldown, and the fight becomes a slower duel.

So the card is never judged by its stat line. It is judged by how it lands in a ten-second loop where the player is also watching for a white flash.

One rule I set: cards are not designed from other cards. Card text is the space that has already been mined, and designing from it produces recombinations of existing effects. The mechanics files are where the unexploited design space lives — the interrupt rule, the readiness queue, the formation table — because each is a lever no card may have pulled yet. That is written into the project's own design instructions, not just into my habits.

What I built

A staged damage-resolution pipeline

Damage is not a subtraction. It runs through an ordered pipeline of stages — IDamageStage implementations split into base, hero and monster sets — with a DamageContext carrying the in-flight values and a DamageResult exposing the outcome to whatever asked.

The alternative I rejected: the usual TakeDamage(int) with a growing pile of special cases inside it. That function becomes unreadable at about the fifth mechanic and untestable immediately, and every new status effect risks reordering something invisible. Staging makes the order explicit and the interactions inspectable — which matters when 24 status effects, 13 keywords and 33 relics can all touch the same hit.

It also means a spell handler asks the result what happened rather than recomputing it. Crit is a flat 2× multiplier applied in the pipeline; elements, armor and block all resolve in known positions.

102 cards, 33 relics, and the constraint that keeps them honest

The catalogue is large: 102 spells, 33 relics, 24 status effects, 13 keywords, 9 encounter types, 8 enemy units — all enumerated in code rather than in a spreadsheet that drifts.

The constraint I imposed on myself is that no design ships without a play walkthrough and an unlock-path placement. A card has to be reasoned through the second-by-second experience of the fight it lands in, and it has to have a place in the progression where a player actually meets it. A card that reads well and has nowhere to live is not finished.

A design bible that cites its own source code

The reasoning behind the systems lives in design-bible/ — combat feel, reference scenarios, and a systems-rationale log recording why each rule exists. Every number in it carries the file and constant it came from, so it can be re-verified when tuning changes. When a rationale is established during a working session, it gets appended before the session ends.

Design documents rot because they restate values that later move in code. Citing the source turns the document into something checkable, and a rule whose rationale is recorded cannot be silently reintroduced after being engineered out.

The pacing targets it protects are explicit: regular fights 20s–1:30, elites 40s–2min, bosses 1–3min, a biome 5–10min, a full three-biome run 15–30 minutes — chosen for mobile sessions. Deck size runs 8–20 cards, with trimming treated as good play.

Balance is designed for the real distribution, not the ideal one. Most players land 10–20% of available parries and good players 30–40%, so parry payoffs are priced for that band rather than for expert play. Perfect play is meant to zero out easy and normal fights; elites and bosses are supposed to land damage on everyone, and some attacks deliberately resist perfect armor play so that the second defensive layers have a reason to exist.

The unglamorous half: shipping it

Most of the work between a prototype that runs and a product that ships is here.

  • Versioned save-schema migrations — MetaProfile.CurrentSchemaVersion plus a ProfileMigrator. A roguelike accumulates meta-progression, and an update that eats a player's unlocks is unrecoverable trust damage.
  • Google Play identity and cloud sync — GooglePlayIdentity, CloudSyncService.
  • Live-ops SDKs integrated: Cloud Save, Leaderboards, Analytics, Push, IAP and LevelPlay ads.
  • Store compliance authored, not skipped — privacy policy and data-deletion pages, which is a public repository of its own.
  • Play App Signing configured through an upload keystore, and signed release AABs cut at v0.4.4, v0.5.0 and v0.5.1.
  • ~24 UI screen scripts, 4 game scenes, 26 prefabs, 431 sprites.

The tooling around it

Building this game alone is also what produced the AI work. The UI Harness — a gated multi-agent pipeline that turns a written brief into a built, validated Unity screen — exists because authoring screens for this game was the bottleneck, and it writes into this repository. It has its own case study, which covers the engineering.

Two things are worth saying here rather than there:

  • The tooling is judged by whether the game shipped, not by whether the pipeline is interesting. It writes into a repository I release from, which is why it has human gates and validators instead of autonomy.
  • I did not use a model where determinism was correct. chrome-gen, the sprite generator in the same toolchain, is deterministic with pixel-exact diff verification. Choosing not to use generative AI is also a design decision, and on that problem it was the right one.

Scope

  • Release. In closed testing on Google Play with the required 12 testers; the 14-day clock is running.
  • Numbers. Everything above is engineering and design measurement.
  • Team. Built alone. Stepland is the work inside a team.
  • Balance. Reasoned and playtested. The pacing and parry-rate figures are my own measurement.

Purple Pwny — a game-playing agent, a biome, and a browser game's Unity client

Terminology. The agent below is an expert system. Rules and utility scoring, hand-tuned by me, encoding how I play. There is no learning component and no model. That codebase does contain a genuine genetic optimiser and a forward-search solver. Neither is mine.

Summary

Purple Pwny Studios is an independent for-hire studio whose products include Degen Dungeons. I worked there August 2023 to October 2024 — starting on concept art, then committing code from September 2023 — as a gameplay programmer inside a self-hosted 2,710-commit codebase built mainly by one other engineer over the preceding year.

Three pieces of that work are worth showing:

  1. DunAI — a 552-line decision agent that plays the dungeon crawler competently, written in a single commit and essentially untouched since. It exists so the game could be measured against skilled play instead of random play.
  2. The Seashore biome — its enemy roster, its boss, its signature status mechanic, and the balance pass — plus ~20 relics I designed and implemented, with the engine changes needed to support them.
  3. The Degen Drafts Unity client, built end to end — about 86% of its ~2,680 lines, including a generator that inverse-simulates a race from a predetermined winner.

The game is public at degendungeons.com.

The agent

DunAI.cs is 552 lines. I wrote it in one commit in April 2024, and line-level blame is 427 mine to 124 — the 124 being a later formatting pass by someone else, not a change of behaviour.

The problem it solves. A roguelike's balance question is "how does this item perform in the hands of someone who knows what they are doing?" Simulating with random play answers a different and much easier question. You need a player, at volume — and a human cannot play ten thousand dungeons.

What it is. A rule tree branching per landmark type with explicit thresholds, sitting on closed-form utility scoring. Weapon evaluation is damage × speed × (accuracy / 100) with multiplicative bonus adjustments over hand-tuned per-stat coefficient tables. Shop policy is a value lookup — buy when cost <= relicValue, ranked by relic_value / basePrice(rarity) — against DunAIDB, a 356-line table of per-class relic gold values code-generated from a spreadsheet the designers actually maintained.

Why hand-authored was the right call. The goal was not to discover optimal play. It was to encode known competent play so that item performance could be measured against a stable, inspectable baseline. A learned policy would have been a second thing to debug, and when balance numbers came out strange there would be no way to tell whether the item was wrong or the policy had drifted. Rules can be read. When this agent does something surprising, the reason is in the file.

The source carries a note I wrote on the agent's own behaviour:

// 90% optimized. I could test for specific curses…

Written at the time, to myself, in a file nobody was auditing. It says the agent is good enough for its purpose and names the gap that remains — which is the calibration I would want from anyone shipping a heuristic.

Attribution. The same repository contains a forward-search solver, a batch balance harness that runs ten thousand dungeons per item, and a genetic algorithm fitting a target death distribution. All three are the other engineer's work. My agent is invoked by a runner flag, and the repository keeps no report artifacts, so what shipped from its output is not recorded there.

The Seashore biome, and ~20 relics

The biome. I authored the Seashore row — a fast, evasive, ability-damage-leaning coast with the boss Chef Scampi — its six enemy definitions, and the TENDER ("Tenderize") status mechanic threaded through the whole biome so the enemies, the boss and the player's counterplay all referenced one idea rather than each having their own.

The boss ability, StirFry.cs, is entirely mine: a stateful two-mode ability that either self-buffs by composing three effect instances or deals 200% damage if already Heated, with an OnReceiveDamage override that strips the buff on a critical hit. That last clause is the design — it gives the player a specific, learnable answer to the boss's escalation instead of a damage race.

Scope: my contribution is the mechanical and balance layer. The biome's tileset is not mine; its map builder is a stub inheriting the forest one.

The relics. Around 20 implementations, 13 of them files with no one else's commits: BargainingChip, CursedClaymore, CursedGrimoire, DoubleEdgedSword, GoldenChalice, LuckyCharm, OldRevolver, PiggyBank, RustyShield, SacredMace, TrinketOfBrutality, UnityStone, VIPPass, and more.

These were designed, not ticketed. The brief was a list of relic names and existing icon art: design an effect that suits the name and the art and makes sense inside the game's existing ecosystem. So the mechanic was mine to invent, constrained by a name and a picture — which is a harder and more interesting constraint than a spec, because the fantasy is fixed before the mechanic exists.

And they came with engine work. Several effects had no support in the engine, so I extended it: a FLAT_PRICES cell for shop discounts, WalletChangeReason threaded through currency actions so a spend could be attributed, and GetSellPrice. That is the part of content work that does not show in a design document — the content is only as good as the systems willing to express it, and if you cannot go down a layer you end up designing what the engine already permits.

Degen Drafts — the Unity client, end to end

Degen Drafts is a betting game around a race. I built its Unity client end to end — about 2,319 of its ~2,680 lines, with the round kernel, the odds table, the season kernel and the EV simulator being separate libraries written by the other engineer. The odds work is not mine.

The interesting piece is BehaviourGenerator.cs — 339 lines, 338 mine. The race outcome is decided before the race is shown, which is a provably-fair requirement, not a design choice. So the generator runs the problem backwards: from a predetermined winner it derives drink times, builds per-contestant behaviour timelines — drink stages, cough distractions — and computes progress curves that arrive in the right order.

Its own comment states the goal: to create tension and story — was it close, was it a brutal victory. That is the constraint that makes it difficult: the outcome is fixed before the race is drawn, and it still has to play as a race. A correct result that reads as a foregone conclusion is a failed feature.

Also mine: BaseState.cs, a state machine over a game-event enum (ROUND_START → BETTING → DRINKING → CELEBRATION → PRIZE → DONE), 290 of 306 lines; DraftsRNG.cs, seeded deterministic RNG composing a server season seed, a round seed and a monotonic counter, 100% mine — including its own written caveats about bias I had not tested; and the UI, text, coin, bet, banner, progress-bar, scheduler and scene-loading managers. I also contributed to the WebGL↔JS bridge and the Drafts web page, where the bridge concept was not mine.

On the bet multipliers: the committed code has 2×, 3×, 4× and 5× across two arrangements. I have said "up to 7×" from memory in the past; the repository does not support it, so 2×–5× is what I use.

What I learned from the codebase, as distinct from what I built

Worth naming because it shaped how I work, and because it is context rather than authorship: the project was server-authoritative, with a SERVER compile flag gating oracle code out of the client entirely; outcomes were provably fair, decoded from a hash chain; and determinism was a first-class concern, with DNA snapshot/restore across five aggregates and a desync fuzzer to catch drift.

That was my first exposure to a codebase where "it works on my machine" is not a defect report but a category error. None of that architecture is mine. Working inside it for a year is why the systems I have built since are deterministic where they can be and instrumented where they cannot.

Scope

  • Seniority. My first professional role, in a codebase largely written before I arrived: 78 commits against 2,594. The commits are large — the agent landed as a single +552-line file — but the shape of the system was set before me.
  • The agent. Rules and utility scoring. No training, no model, no optimiser.
  • Balance outcomes. The agent was built to run at volume; the repository keeps no report artifacts, so this page describes the tool rather than its results.
  • Not mine. The biome tileset, the odds and EV work, and the live chat.
