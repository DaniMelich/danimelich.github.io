A 16-agent fleet that runs overnight, and the cost programme that made it affordable

The system this one replaced verified its own work with fifteen validator modules and half its budget, and the telemetry said it was catching nothing (the write-up is here). Deleting it left the real question exposed: how much work can one person direct in a night and still stand behind at merge time? The limit is not what the models can write. It is that parallel agents collide in a shared Unity repository, that a human can only be in one place, and that spend scales with context rather than with output.

The fleet is the answer I built to that, on a game repository of ~47,500 lines of C# and 582 commits.

Agents collide in the repository before they collide in the model

Two agents editing the same Unity scene, prefab or .meta file produce a merge conflict no model resolves well. So the topology came from the repository's own history: the fleet plan runs a co-change analysis over the last 300 commits and derives the lanes from which files actually move together. The result is one serial lane for Unity-owned assets, where only one writer is ever active, and four parallel lanes in git worktrees where the file sets do not overlap.

Sixteen agent definitions sit on top of that, each pinned to a model tier chosen by cost of failure rather than by task difficulty — the plan's own criterion is what it costs to be wrong, so review-and-audit roles run on the strongest tier and mechanical roles do not.

Every dispatch returns the same contract

An agent that finishes and writes a paragraph about what it did is not reviewable at fleet width. Every dispatch returns a fixed structure: the issue, the branch, the files touched, which cheap-CI tier it needs, whether it needs the Unity gate, what to verify, a confidence level, and anything it noticed that was outside its scope. The last field is the one that earns its place — out-of-scope findings become the next night's issues instead of dying in a transcript.

Five hooks (705 lines) are wired into the session lifecycle around this: context warnings, localisation export, docs indexing, feedback capture, and a guard that keeps an agent inside its own worktree. Verification is a six-job CI, including negative self-tests that fail if a check has stopped being able to fail.

The gates are cheap first, and human where the human changes the answer

Each returned contract names its own cheap-CI tier, so a documentation change is not paying for a full build and a scene change is not skipping one. One human gate is kept: the Unity lane, where what a screen looks like running on a device is information no check in the pipeline holds. Everything the compiler, the filesystem or CI can settle is settled there, because those answers are free and they are not opinions.

A full-width night

On 2026-08-30 the fleet ran at full width for the first time: 107 commits merged in a single day, across audit and worktree branches. On the Claude-task path, the project's own write-up records 25 pull requests merged in one night.

The plan recorded the expected gain before that run rather than after it — 2 to 2.5×, explicitly "not a 5x night" — so the result had a prediction to be measured against.

The limit on a fleet like this is context spend, and it is measurable

Running agents unattended overnight turns model spend into an operating cost, and an operating cost is something to measure before optimising. I ran a 30-day measurement over my own session logs, deduplicated by request ID, and bucketed spend by context size. The curve is steep — cost per turn rises by roughly 6× between the smallest and the largest context bucket — and the high-context end was carrying 42.0% of the bill.

The levers were then ranked by measured saving, not by which one looked cleanest to implement: model routing first, then automatic compaction, then read discipline, then handoff structure — and startup-prompt trimming, the change that looks most obvious, last, roughly 18× weaker than the strongest lever.

Shipping the top of that list and re-measuring the same way produced the result the programme was written to test: that share fell from 42.0% to 12.1%, against a 20% bar set before the work. Per-bucket cost per turn was unchanged, which is the point — the work moved turns to where they were already cheap rather than making expensive turns cheaper. (Both measurement windows are computed by one script over session logs held outside the repository; the method and the numbers are in the project's shipped token-efficiency document.)

A gate that failed

Part of that cost work was testing whether local models could take the cheap end of the routing. The intent classifier had an 80-item labelled evaluation set and a hard accuracy gate of 0.95, written before the candidates were run. Two quantised local models scored 77.5% and 85.0%. Both failed the gate, the per-item misses were recorded with reasons, and neither model was integrated — the routing work went to the levers that had passed their own measurement instead.

What this is evidence of

I build multi-agent systems that run unattended against a real product: topology derived from how the codebase actually changes, a dispatch contract that makes every agent's output reviewable, gates priced so the cheap check runs first and the human is spent where only a human helps, and cost measured as a curve with levers ranked by their measured return. The gates are written to be able to fail, and when one does, the thing it was gating does not ship.

The UI pipeline that shipped screens — and the telemetry that ended it

Getting an agent to write a Unity screen is not the hard part. Getting output you can put into a shipping game without reading every line of it is: somewhere between the written brief and the merge, something has to establish that the code compiles, that the layout is the one that was approved, and that the art is the art that was asked for. I built that verification layer, instrumented it, and then deleted it — because the instrumentation said it wasn't catching anything.

At archival the system was ~35,000 lines of Python across 88 modules: 20 pipeline stages, five human gates, 15 validator modules and roughly 1,080 tests, driven from a desktop operator application of ~31,000 lines (Tauri/Rust, a React renderer and a Python sidecar). It is all recoverable from the repository's history. None of it runs today.

Typed contracts crossed every stage boundary, not prose

A stage could not hand the next stage text it had invented. Handoffs were Pydantic models — a 1,070-line strict-typed contract file — with Markdown and HTML generated as views of the object, never as the source. An artifact was content-addressed by its inputs, so a rerun of an unchanged stage was identifiable as one.

Five human gates sat on the path: readiness, sketch, layout, art, final. A rejection routed back to the stage that caused it rather than to the top of the graph, and it could be anchored to an element — reject --annotate "HeroCard: portrait is cropped" applied as a minimal JSON-Patch on the presented contract, leaving everything unannotated intact and listing the exact delta when the gate re-raised.

Both are artifacts of one recorded run of the archived pipeline.

It put screens into the game, and it reported what they cost

Three screens went end to end and were accepted by a human reviewer; both screen families landed in the game in August 2026. Each run wrote its own KPI report, so the pipeline stated its unit economics rather than leaving them to be estimated: $67–98 per accepted screen, with rerun spend attributed to validator, human or crash.

That attribution is the reason this page exists. Reruns cost close to twice the first pass, and most of the rerun bill was validator-driven. Knowing which of the three causes was paying made the next decision an arithmetic problem instead of an argument.

The parts I could score against a human, I scored

The pipeline recorded whether its automated visual judge and the human reached the same verdict, per run. Across the three accepted runs they agreed once. On one run the judge passed a screen the human rejected; on another it failed a screen the human accepted. Those disagreements were the input to the next round of rubric work, and they are the reason the judge score was never treated as an acceptance criterion on its own.

Retrieval was scored the same way: hybrid dense and lexical search over a local index, fused by reciprocal rank, measured against a 32-pair gold set built from real failure history with queries deliberately not phrased in the target entries' wording — recall@10 0.969, MRR 0.663 (archived-system measurement).

The verification layer was the expensive half, and it had not caught anything

In August I audited three complete runs against the pipeline's own telemetry. The cross-check validators — the layer that compared one stage's output against another's — produced no confirmed true positives across 730 findings. Over the same runs, validator-triggered reruns accounted for 48–51% of spend, and stages sat idle 93–97% of wall-clock time waiting on those checks. A large share of the findings the system logged about itself were plumbing bugs in the harness rather than defects in model output. (These figures are measured in the project's ratified archival plan, from run data held outside the repository.)

The layer was doing what I had designed it to do. It was reading a model's output with another model and reporting differences, and a difference from a contract is not the same thing as a defect. The cheap deterministic checks — does it compile, does the asset exist, does the scene contain the component — were catching the real failures on their own.

So I deleted it

On 2026-08-27 the pipeline and its operator app came out of the project in one commit: 1,240 files, 162,256 lines removed. Verification moved down onto ground truth — the C# compiler, the filesystem, the live Unity scene — and into a six-job CI that runs on every change, including negative self-tests that fail if a check stops being able to fail.

Three things carried over, because the telemetry supported them: typed contracts as the handoff format, human gates placed only where the human's answer changes the output, and cost attribution from the first run rather than after the bill arrives. The successor ships more work per night than this system did, with a fraction of the machinery — it is written up in agent-fleet.md.

What this is evidence of

I build agent systems with the measurement in place before the features, and I hold my own components to the catch rate they were built to deliver. A checking layer that cannot show what it caught against the human's recorded decisions does not stay in the system, however much of it I wrote. The judgement that mattered here was not the architecture — it was being able to read a cost ledger and a findings log and conclude that the answer was less system, not more.

Stepland — owning the number a live commercial game's economy runs on

Godot 4.6 · iOS and Android · one of three core programmers inside a larger team · eight months, 2025–2026

Stepland turns real-world walking, hydration, meditation and exercise into a Tamagotchi-like pet. Every currency, streak, reward and progression beat in it is downstream of one number — how many steps the player actually took. When I joined, that number arrived through Google Health Connect, a third-party hub that could report connected while delivering zero steps.

To the player, that is not a misconfigured hub. That is Stepland being broken, at first launch, before they have seen the game.

The app is live on Google Play and the Apple App Store. Anyone can install it and check every shipped screen on this page.

Owning the step counter instead of renting it

The dependency cost us players at the most expensive moment there is. A large share of players did not have Health Connect installed at all. It is only a hub, so it needs its own separate step-recording connector behind it — onboarding became a two-app setup unrelated to Stepland. And misconfiguration failed silently: the app reported success while the core mechanic did no work, and the player attributes that to the app in front of them.

I proposed reading the Android pedometer directly instead. It was a significant architectural change and the team wanted to exhaust the existing approach first, which took about four months. When it was agreed, I built the replacement in a week, in Kotlin, a language I had not written before, working from references and pattern recognition.

The in-house path is mine: the sensor reader, the WorkManager snapshot scheduler and the background worker that keeps steps accruing with the app closed, plus the Godot↔Android bridge and the runtime permissions around them. What shipped carries no third-party dependency, no second app and no silent zero-step state — one "allow pedometer access" prompt at first launch. It has been stable since.

The argument for owning this was never that third-party code is bad. It was that this particular failure mode was silent on our side and unambiguous to the player.

Rebuilding the tutorial to a showcase date

The tutorial built earlier in the project had been outgrown. I built its replacement as 82 declarative steps across 32 polymorphic step classes, behind a sequence runner with resume-from-index and per-step telemetry.

It is declarative on purpose. A tutorial that is a hard-coded sequence of special cases cannot be reordered, A/B-tested or resumed. With each step as a class behind a runner, the tutorial becomes data — and resume-from-index means a player who drops out of onboarding does not start it over, which is the point at which tutorials usually lose people.

I delivered it by driving coding-agent sessions in the production repository and owning the result. It landed on the opening day of the 4YFN showcase, immediately before the release candidate was cut: agent-assisted implementation in a shipping commercial codebase, against a date that did not move.

Art was being made before the requirements existed

Product intent was reaching the concept artist directly, so full-fidelity art was produced before requirements were settled — then reworked weeks later when a missing button or a missing state turned up. The art was not the problem. The order was.

I put a stage in between. For each new screen or feature I produced a structural mockup without final art — in Figma, or as plain Panel blockouts built directly in Godot with basic functionality — which the artist then dressed. Requirements got argued while they were still cheap to change.

The shipped screen keeps the layout I specified: title-plus-tagline header, scrolling level list with per-row star ratings and reward chips, locked-row treatment, daily-rewards-remaining line, and the close affordance.

Again the skeleton shipped: completion banner, rewards block, and a two-button footer whose second button is the rewarded-ad double ("Bonus de Recompensa!" → "DOUBLE REWARD"). The structure is mine; the art and the final refinement are the artist's. I specified what had to be on each screen and how it was arranged, before anything was drawn.

The streak screen shipped as I blocked it out

This one is not a mockup that was replaced. I blocked it out directly in Godot and it is still live, essentially unchanged, in a commercial product. The streak feature behind it is mine end to end — service, data model, the whole UI, and a 204-line test suite covering 14 cases.

The design half of the job

I was not only implementing features handed to me. The design work is written down, and it reasons about retention rather than describing screens:

  • A diagnosed onboarding problem. The first-time experience "feels like following a check-list" and runs out in 5–10 minutes, before the player is hooked — against a stated target of holding a player for at least 30 minutes.
  • Return timing as a design problem. The player has no way of knowing when to come back, so the design prescribes an explicit time horizon, in-app step feedback as a proxy for idle progress, and a notification at the moment the resource fills.
  • A two-tier task system with a purpose per tier — progress tasks give direction, daily tasks give a reason to return — staged with escalating rewards, tied to both real-world and in-game actions, with premium currency deliberately placed on the behaviours the game wants to reinforce.
  • Economy work in the working vocabulary: revising sources and sinks, and the specific diagnosis that the game had many one-time sources, many recurring sources and many one-time sinks, but lacked recurring sinks.
  • Never pure RNG. NPCs get recurrent, discoverable patterns: players who read randomness disengage, players who read a pattern keep playing.

The loop closes on the task system. I specified the two tiers, argued for them, then created tasks_service.gd from nothing along with all 25 task definitions, five resource classes and the task UI.

Dungeon Heroes — meta-economy, save migration and combat systems for a free-to-play Android roguelike

Unity 6 · C# · Android · solo · 2025 →

The hard part of a free-to-play game is not the fight. It is everything that has to stay true after it: a player's account survives every update, the drop odds are a number a designer wrote down rather than a property of a random roll, and balance changes come from run data instead of from how the developer happens to play. Those are the systems a one-person project normally skips, and skipping them is what makes most solo projects useless as evidence.

Dungeon Heroes is a real-time action roguelike whose abilities arrive as cycling cards. I own all of it — combat, the meta-economy, save migration, telemetry, the content tooling, the live-ops integration and the store compliance — through to signed Android release builds.

Damage is a pipeline, not a subtraction

Cards are played inside a live fight. Casting locks the hero for the length of the cast, so the real cost of a card is the defence given up while it resolves, and a successful parry pays energy back. That loop is the reason the catalogue cannot be a stat table: 174 spells, 52 status effects and 38 relics across 4 heroes all reach into the same hit.

The usual shape — TakeDamage(int) with a growing pile of special cases — stops being readable at about the fifth mechanic and stops being testable immediately, and every new status risks silently reordering something that already worked. Damage instead resolves through ordered IDamageStage implementations, with a DamageContext carrying the in-flight values and a DamageResult the caller reads rather than recomputes.

The order is therefore explicit and the interactions are inspectable. A new status effect is a stage in a known position rather than another branch inside a function that has already outgrown review, and a spell handler asks the result what happened instead of duplicating the maths.

The fight is tuned in tenths of a second

Real-time combat on a phone has one governing constraint: the player's eyes are on enemy wind-ups, not on the hand, so every number in the fight decides whether a half-second of attention is enough to act on. None of those numbers is an engine default. Each is an authored constant, and each is recorded in the design bible with its source in code, so a tuning change is re-verifiable rather than a matter of memory.

The clock behind the card loop is explicit. Cast locks run 0.42 seconds for the fastest attack to 1.5 for the big heal, so a long cast is a real bet that no tell lands inside it. Enemies act one at a time through a queue that enforces a 1.5-second gap after every action, and each enemy then waits out its own authored cooldown — most in a five-to-nine-second band — so pressure arrives as a sequence of individually answerable questions instead of a pile-up. Energy caps at 4 and regenerates at 0.5 per second: the rate is set so that parrying, not waiting, is how a player earns the right to cast more.

Tell timing is a banded system rather than a per-enemy guess: wind-up holds of 0.15–0.25 seconds, a parry flash 0.25–1.3 seconds before impact, and the easiest reads on a 0.6–0.7-second plateau with difficulty rising toward both ends of the band. That plateau came out of play, not out of the first draft — the earlier "easiest" constant sat on the hard short shoulder of the curve, and every enemy authored to it was near the hardest legal read — which is the difference between constants that were chosen once and constants that are maintained. The targets they all serve are written down too: regular fights at 20 seconds to a minute and a half, full runs at 15–30 minutes of mobile session, parry payoffs designed for the 10–20% landing rate most players manage rather than the 30–40% of good ones. When the fight feels wrong, there is a named constant to argue about.

The odds are authored, not emergent

The meta layer is 34 files and roughly 8,100 lines: a chest engine with authored odds tables, a pity timer and a featured 50/50; a smithing star ladder; a talent tree, constellations, hero loadouts, and five currencies that feed each other.

The pity timer and the 50/50 are the parts that decide whether a player trusts the box. A bad streak has a floor, and that floor is a value in a table someone chose — which means it can be tuned, stated to the player, and reasoned about when the economy shifts — rather than a behaviour that emerges from the roll and has to be discovered by simulation. The same discipline runs through the upgrade ladder and the currency sinks: progression is one system with one set of tunable tables, not a row of features sitting beside the run.

A save file has to survive every update

Meta-progression is the thing a player would not forgive losing, so the profile is versioned and migrated rather than overwritten. ProfileMigrator carries a save from v1 through v2 to v3, checks that re-running a migration is idempotent — a migration that executes twice must not grant its rewards twice — and refuses a profile written by a newer client outright instead of reading it partially. A schema validator runs over the result.

Underneath it, the profile store is an interface with a local implementation and a cloud sync path against Unity Gaming Services, keyed to Google Play identity. The migration work is what makes cloud save safe to switch on at all: two devices at different client versions is the normal case, not the edge case.

The balance analyzer refuses my own runs

Every run emits a schema-versioned RunRecord — about thirty fields, with enums crossing the wire as names rather than ordinals, so that reordering an enum later cannot silently rewrite the history. An offline analyzer aggregates them.

That analyzer rejects runs recorded in the Editor or on a development machine as balance signal, and prints a banner that cannot be suppressed when it does. The developer is simultaneously the most over-represented player in the data and the least representative one; left in, my runs would dominate every aggregate and quietly pull each tuning decision towards how I play. Excluding them by default means a balance change has a denominator I can name.

Content volume is the bottleneck, so the tooling is part of the game

There are 519 animation clips across 63 animator controllers. They are not hand-wired: a 1,325-line animator builder generates them, and timing validators check clip timings against the cast windows they have to match, so a mismatch is a failed validation rather than a fight that feels wrong three weeks later. 920 localized rows in English and Spanish across six sheets cover spells, meta screens, keywords, UI and items.

Adding an enemy or a spell is a tool run plus a data row. That is what keeps a catalogue this size from freezing the design.

Live-ops is wired before launch, not after

Cloud save, Google Play identity, analytics with consent, ads and in-app purchases are integrated, and a Remote Config version check gates the client at the main menu so a build can be required forward before a player starts a run. The privacy policy and data-deletion pages are written and published from their own public repository, and the release process is written down as a runbook rather than held in my head.

Eight signed Android release artifacts sit in the build directory, from the v0.4.4 AAB through the v0.5.6 APK, on Play App Signing with an upload keystore.

The tooling behind the throughput

The width of this — ~47,500 lines of C# across 188 scripts, 582 commits since July 2025 — is held by tooling I built for this repository: a fleet of 16 agent definitions dispatched across one serial Unity lane and four worktree lanes, each task returning a structured contract, all of it behind human gates and a six-job CI with negative self-tests. On 30 August 2026, its first full-width day, 107 commits merged. It has its own case study; what matters here is that it writes into a repository I cut release builds from, which is why it is gated rather than autonomous, and why the design decisions above are still decisions rather than generated defaults.

The systems a live F2P team hires for, owned end to end

Economy and progression with authored odds and named sinks. Save-schema migration written for players who already have something to lose. Telemetry with a defined balance denominator. The live-ops SDK surface and the store compliance around it. A combat core that is still extensible past 170 spells.

In a studio those are usually four people's areas. Here they had to interoperate on one codebase, so I own the seams between them as well as the parts.

Purple Pwny — balancing a roguelike against an agent that plays it properly

C#, Unity · gameplay programmer inside an established production codebase · 2023–2024 · the game is public at degendungeons.com

A roguelike's balance question is never "is this item strong?" It is "how does this item perform in the hands of someone who knows what they are doing?" Simulating with random play answers a much easier and much less useful question — and no human is going to play ten thousand dungeons. To balance the game, the game needed a player.

The agent

I wrote DunAI: 552 lines, delivered in a single commit, essentially untouched since — a decision agent that plays the dungeon crawler competently, so item performance could be simulated against skilled play instead of random play.

It is an expert system. A rule tree branching per landmark type with explicit thresholds, sitting on closed-form utility scoring: weapons are evaluated as damage × speed × (accuracy / 100) with multiplicative bonus adjustments over hand-tuned per-stat coefficient tables. Shop policy is a value lookup — buy when cost <= relicValue, ranked by relic_value / basePrice(rarity) — against DunAIDB, a 356-line table of per-class relic gold values code-generated from the spreadsheet the designers actually maintained, so the agent's economy stayed the designers' economy.

Why rules rather than a learned policy. The goal was not to discover optimal play; it was to encode known competent play, so that item performance could be measured against a stable, inspectable baseline. A learned policy is a second thing to debug: when a balance number comes out strange, you cannot tell whether the item is wrong or the policy has drifted. Rules can be read. When this agent does something surprising, the reason is in the file.

The source carries a note I wrote on the agent's own behaviour:

// 90% optimized. I could test for specific curses…

It marks where the policy stops being optimal, which is the thing anyone tuning against a heuristic needs to know before they trust its output.

The Seashore biome, and around twenty relics

The biome. I authored the Seashore row — a fast, evasive, ability-damage-leaning coast with the boss Chef Scampi — its six enemy definitions, its balance pass, and the TENDER ("Tenderize") status mechanic threaded through all of it, so the enemies, the boss and the player's counterplay all referenced one idea instead of each carrying its own.

The boss ability, StirFry.cs, is a stateful two-mode ability I wrote end to end: it self-buffs by composing three effect instances, or deals 200% damage if the boss is already Heated, and an OnReceiveDamage override strips the buff on a critical hit. That last clause is the design — it gives the player a specific, learnable answer to the boss's escalation instead of a damage race.

The relics — designed, not ticketed. The brief was a list of relic names and existing icon art: design an effect that suits the name and the art and makes sense inside the game's existing ecosystem. The mechanic was mine to invent, constrained by a name and a picture, which is a harder brief than a spec, because the fantasy is fixed before the mechanic exists. BargainingChip, CursedClaymore, DoubleEdgedSword, PiggyBank, VIPPass and about fifteen more shipped.

And they came with engine work. Several effects had no support in the engine, so I extended it: a FLAT_PRICES cell so a relic could rewrite shop pricing, WalletChangeReason threaded through currency actions so a spend could be attributed to its cause, and GetSellPrice. Designing content in someone else's engine means either going down a layer or restricting yourself to what the engine already permits.

Degen Drafts — the Unity client, end to end

Degen Drafts is a betting game around a race, and its central constraint is that the winner is decided before the race is shown. That is a provably-fair requirement, not a design choice — and the race still has to play as a race. A correct result that reads as a foregone conclusion is a failed feature.

I built the Unity client end to end. The piece that constraint lands on is BehaviourGenerator.cs, which runs the problem backwards: from a predetermined winner it derives drink times, builds per-contestant behaviour timelines — drink stages, cough distractions — and computes progress curves that arrive in the right order while the race still reads as contested. Its own comment states the goal: to create tension and story, was it close, was it a brutal victory.

Around it, also mine:

  • BaseState.cs — the client's state machine over a game-event enum (ROUND_START → BETTING → DRINKING → CELEBRATION → PRIZE → DONE), so every phase of a round is an explicit state rather than a set of flags read from three places.
  • DraftsRNG.cs — seeded deterministic RNG composing a server season seed, a round seed and a monotonic counter, so a round can be reproduced exactly from its seeds.
  • The UI, text, coin, bet, banner, progress-bar, scheduler and scene-loading managers, plus contributions to the WebGL↔JS bridge and the Drafts web page.

Server-authoritative, provably fair, deterministic

The codebase I joined was server-authoritative, with a SERVER compile flag keeping oracle code out of the client entirely; outcomes were provably fair, decoded from a hash chain; and determinism was a first-class concern, with DNA snapshot/restore across five aggregates and a desync fuzzer to catch drift. It was my first year in a codebase where "it works on my machine" is not a defect report but a category error.

That is why the systems I have built since are deterministic where they can be and instrumented where they cannot — and why, when I am handed a balance question, my first move is to build the thing that can measure it rather than to start adjusting numbers.

What this is evidence of

  • Content design under production constraints. A biome, a boss and around twenty relics shipped inside an engine I did not write — extending the engine where a design demanded it rather than trimming the design to what the engine already allowed.
  • Building the instrument before tuning. The agent exists because a balance question deserved a measurement. The same move recurs in my later work: the Monte Carlo calibration behind Dungeon Heroes' balance agent, and the evaluation gates in the agent tooling.
  • Simulation-driven agent work dated 2024. A hand-authored policy, inspectable by design — the case for rules over a learned policy is argued above, not assumed.
